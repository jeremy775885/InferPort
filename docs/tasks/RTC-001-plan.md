## 1. 目标与授权边界

交付可选择启用的 RTC 能力：执行端按自己的时间线持续消费动作，同时请求下一块；
服务端根据明确的旧计划构建硬前缀，返回一个或多个候选；执行端只接纳仍与执行历史
一致的候选。普通 InferPort 同步调用继续可用，运行时不引入 Torch 或机器人 SDK。

本轮只编写计划与任务入口。实现、GPU 测量、仿真/真机运行、Git 提交及发布均未启动。
批准计划后仍按所选执行范围工作；跨仓库接入和设备/资源选择不能由本文件自动授权。

## 2. 建议采用的第一版范围

以下为本计划的推荐决策，批准前不视为用户已选实现：

| 项目 | 推荐选择 |
| --- | --- |
| 推理调度 | 固定动作步周期 p，一个在途逻辑请求；不积压旧观测请求 |
| 候选 | 一次请求可以有 B 个前缀长度；B=1 是同一实现的普通情况 |
| 候选交付 | 一次响应返回完整候选集合，client 最终选择；不增加流式响应 |
| 动作时间 | 固定模型动作周期 Δt；与底层伺服频率区分；明确动作起点与边界 |
| 执行时钟 | `realtime` 与 `simulation_pause` 两种明确模式 |
| 前缀来源 | 支持显式数组和带身份的服务端缓存引用；不做静默回退 |
| 模型计算 | 第一版不绑定 GPU 拓扑；模型适配器负责批量计算，先验证单候选和 CPU 假模型 |
| 传输 | 保持当前 WebSocket、消息封装和单连接所有权；RTC 是可选上层契约 |
| 真机违约 | 不再消费旧 chunk；进入执行端定义的安全等待/停止状态，显式恢复 |
| 仿真违约 | 在承诺窗口结束前冻结完整环境时间，等待可用结果；保留有限通信超时 |

多卡内部计算可以符合相同的整批响应契约，但本轮不直接实现 GPU 池、模型切分或
逐候选抢先返回。动态 p、在线自动调整前缀集合、不同观测的并发请求保持为后续方案。
用户已明确暂缓共享内存；不增加 ZMQ/socket 后端、通用传输插件或 Guided RTC 算法。
这些边界不影响在本版契约中完整表达多个 d 候选。

## 3. 实施事实与依赖

- InferPort 检查基于 766558c、SDK 0.2.0。Client 公共调用阻塞且拒绝并发；服务端
  在同一工作线程调用所有 Backend hooks。关闭连接不等于取消底层模型工作。
- `InferenceSpec` 已能表达嵌套对象、可选字段和有界数值数组；不必为候选引入对象列表
  或重写 codec。跨字段关系须由 RTC 层校验，不能只依赖 shape 检查。
- PI05Std `sample_flow` 当前整批共享 action_prefix.shape[1]，不能表达不同长度；
  公共 `euler_integrate` 已支持逐样本 hard_prefix_mask 与前缀 time=0，应优先复用。
- 当前 LeRobot 服务适配器接受单条 `[prefix_steps,14]` 前缀。多候选需模型与适配器修改，
  仅完成 InferPort 并不等于 PI05Std 已能生成不同前缀的 batch。
- 本机 RoboTwin 的 `policy_evaluation/` 尚未找到；现存 `script/eval_policy_client.py`
  使用 TCP socket/JSON。不能按过往文档假定已存在新版 InferPort client。
  在真实接入阶段先定位用户实际运行的 checkout/入口，再确定修改文件；不改写该旧入口充当新版。

## 4. 时序契约

### 4.1 参数、坐标与验证

以整数模型动作步作为内部坐标。动作块起点为 s，则 c 个动作覆盖 `[s,s+c)`；
第 i 个动作对应 s+i，不得按收到响应的时刻把整块重新编号为零。

| 参数 | 含义/校验 |
| --- | --- |
| Δt | 一个模型动作步对应的执行周期；不是环境内部 physics substep |
| p | 相邻观测快照/推理请求的计划起点间隔，正整数 |
| d_max | 本轮允许旧计划继续执行的最大步数，正整数且小于 c |
| prefix_lengths | 升序、不重复的整数数组 `[d_1,...,d_B]`；正常请求 `1≤d_j≤d_max`，包含 d_max |
| c | 固定完整输出长度，包含硬前缀 |
| n | 本轮观测锚点及新 chunk 起点，同时为快照时下一待执行动作步 |
| k | client 在实际接入边界相对 n 已推进的动作步数 |

第一版固定周期、单个在途请求，配置要求 `d_max≤p` 且 `p+d_max≤c`；
运行时仍须检查源块的实际剩余覆盖，不能仅检查初始化参数。
每个 d_j 还受 checkpoint 训练支持上限约束。启动请求是独立的空前缀特例，见 4.4。

物理时间配置必须先换算成动作步，并明确有效时间。比如 Δt=20ms 时，150ms 的覆盖
需要 ceil(150/20)=8 步，即160ms；不得一边采用160ms窗口，一边仍宣称150ms硬截止。
第一版运行契约只接收显式的整数步参数；转换辅助展示所需覆盖步数/有效时长，调用方
必须选择其接受的有效值。若必须在非动作边界的150ms严格截止，需要另行设计底层中断，
不能由本版动作步调度隐式保证。

### 4.2 正常一轮

1. client 在动作边界形成不可变快照：观测、n、当前采用的源 chunk/候选身份、源位置，
   并记录本地单调时间。实际传感器采样时间也需保留，不能把陈旧图像假装成当前图像。
2. 检查源计划覆盖 `[n,n+d_max)`，复制/锁定这段承诺前缀。此轮处理期间不修改它。
3. 专用 worker 发一个逻辑推理请求；控制循环继续逐步消费承诺前缀，环境 API 仍在
   原执行线程调用。server 的墙钟不推进动作索引。
4. 网络 worker 完成解码后只发布结果；控制线程在动作边界校验并选候选。
5. 原子更新当前计划及未来队列，保留绝对动作索引。新计划的前缀剩余部分继续执行，
   已执行动作不重播；自由生成动作从 `n+d_selected` 开始。
6. 下一轮在 `n+p` 取新观测。若无法满足周期/覆盖，报告调度或执行故障，不积压补发旧请求，
   也不在运行时偷偷把固定 p 改成动态周期。

执行适配器必须区分预取、下发和已经开始执行的动作，不能以取出数组行数冒充执行进度。
第一版要求逐模型动作边界确认消费；若设备提前排队，最早可接入位置必须包含不可撤销
的已下发动作，并证明不会越过承诺窗口。无法满足时拒绝开启该执行模式。

### 4.3 候选选择与边界顺序

候选必须满足：会话和请求匹配；来源快照未失效；形状/单位/有限值正确；硬前缀精确一致；
实际已执行/已承诺动作与候选假设一致；`k≤d_j≤d_max` 且仍有可执行后缀。
满足条件后选最小 d_j。所有检查以 client 实际接入边界为准，不能只看 server model_ms。

例如20ms/步、候选 `{5,6,8}`，105ms收到完整结果、120ms能接入，则 k=6，选择6步候选；
5步候选不保证已执行区间一致，8步候选虽有效但自由生成部分开始更晚。此为逻辑示例，非实测。

每个控制边界按“取已完成结果→校验并原子接入→检查截止→决定本步动作”的顺序处理。
到 `n+d_max` 的提交截点仍无已校验的可用结果，不发该步旧动作，转入等待/故障。
响应恰在边界到达但尚未完成校验，不按成功接入计算；测试覆盖边界两种事件顺序。
实现应预留接收校验与控制调度时间，deadline 不是 server 计算截止时间。

采用一个候选后，其余候选不允许再次更新队列。新的计划只有在下一轮正常请求中作为
来源被引用。不存在“短候选错过就立即全局超时”：只要未到 d_max，仍可等待完整响应
里的较长候选；本版不等待第二份或流式追加响应。

### 4.4 启动与恢复

启动前完成模型 warmup、契约检查和设备安全处理能力校验。首次请求没有源计划，
使用空前缀并只返回一个 c 步块。收到并验证后进入已就绪状态，由执行端明确开始消费。
仿真可冻结环境完成这一步。真机需执行端声明稳定启动条件并持续监管；初始观测与
开始动作间仍有真实耗时，不能把无前缀启动声称为已补偿的稳态 RTC。动态场景不能满足
启动条件时，不自动运行，先确定启动方案。启动同样有有限的请求超时。

真机发生等待/停止后不直接使用迟到结果恢复。清除旧计划引用、刷新观测、建立新 epoch，
重新走启动条件；恢复需要执行端明确发起，不由重连或响应到达自动触发。

### 4.5 两类时钟

- `realtime`：client 单调时钟与模型动作步有已确认的对应关系。deadline 由 client 本地
  监督；执行循环卡住不应靠 server 解救，实际设备必须有适合其控制方式的 watchdog。
  Python 的正常单元测试不能证明硬实时调度保证。
- `simulation_pause`：环境动作步是权威。无结果时最多推进 d_max 步，然后冻结完整环境
  状态/事件时间，等待结果；网络超时仍会终止等待并报告失败。
  在 k=d_max 暂停后通常只剩 d_max 候选可采用。暂停耗时单独统计，不伪装成实时通过。
- 按实时节拍运行的仿真使用 realtime 规则；墙钟与环境步不同速但不暂停的其他模式，
  先明确映射，不能使用 server 时间猜测。

## 5. 协议与服务端缓存

### 5.1 扩展位置

使用现有 `reset/describe/infer`，保持外层 `{id,op,data}` 和错误框架。
新增可选 profile（拟名 `robotics.rtc.v1`）与 `inferport.rtc` 模块。
普通 `Backend/Client` 和 `robotics.joint-targets.v1` 不被强制改成 RTC。

RTC Backend 包装符合候选输入/输出契约的模型 Backend，负责身份、缓存和校验；
模型 Backend 只处理 observation、原始单位 prefix_actions 与 prefix_lengths，返回
候选动作及已声明的可选诊断。模型的加载、预处理与多 GPU 分配仍属于模型适配器。
包装层所有 hooks 继续在现有 backend worker 上执行，模型缓冲区要复制后才能缓存。

### 5.2 固定配置与动态消息（拟议字段）

`describe` 声明 profile、观测 schema、原始动作单位/通道顺序、c/A、最大前缀和候选数的
结构界限。实际支持的 d 与候选集合由 reset 校验；不把普通 shape 校验当作训练支持证明。
模型标识和动作语义参与 session 配置身份。更换模型、归一化或动作语义必须重建会话。

`reset` 的非空 context 配置：唯一 epoch、执行模式、Δt、p、d_max、prefix_lengths、
前缀来源模式、模型适配器原有上下文（指令等）。固定配置不逐请求重复发送。
本版在 epoch 内配置不可变，调整配置走 reset。`reset({})` 仍必须合法：清理会话，
但不建立可推理的 RTC 配置。连接初始化/断开清理继续沿用现有生命周期。

| infer 请求字段 | 作用 |
| --- | --- |
| observation | 当前输入快照，形状由模型契约声明 |
| epoch / request_seq / origin_step | 会话、逻辑请求和输出绝对起点；与外层传输 id 分开 |
| source | 正常请求必填的源引用：bundle_id、candidate_index、bundle_digest、offset |
| prefix_actions | inline 模式必填 `[d_max,A]`；cached 模式不发送；bootstrap 不发送 |
| bootstrap | 明确首块类型；仅允许未建立活动计划时使用 |

source.offset 必须等于 `origin_step-source_origin_step`；slice 范围须完整覆盖 d_max。
请求中的 source 同时确认“client 采用了这个候选”，不新增独立 ACK 往返。
绝对动作编号只在新 epoch 中重置；正常请求要求编号按计划推进，拒绝重放/倒退。

| infer 响应字段 | 作用 |
| --- | --- |
| epoch / request_seq / origin_step | 回显并绑定请求 |
| bundle_id / bundle_digest | 本轮结果集合的不可变身份与内容校验 |
| prefix_lengths | int64 `[B]`；正常请求必须等于会话配置，bootstrap 为 `[0]` |
| actions | float32 `[B,c,A]`，包含完整前缀，使用执行端原始单位 |
| diagnostics（可选） | 模型/服务计时；不作为执行位置或接入许可 |

用数值张量表达候选维度，不为候选数组引入对象列表 schema。字段同现有 ObjectSpec/
TensorSpec 配合即可；互斥字段、B 一致、source 范围、阶段合法性由 RTC 层检查。
服务端结构校验后先完成全部业务验证，再调用可能修改 RNG/模型状态的计算函数。

### 5.3 身份、内容和缓存生命周期

bundle_digest 拟使用 SHA-256，规范化内容包含契约标识、epoch、bundle_id、origin_step、
prefix_lengths、shape、动作通道/单位身份与小端连续 float32 动作字节；编码规则固定并
提供测试向量，不使用不稳定的 Python hash 或含糊的字符串拼接。客户端接收时重算一次，
后续引用只传标识、摘要和切片。摘要用于一致性检查，不代替会话认证或动作时间对齐。

server 缓存不可变结果；client 也保存不可变原始结果，采用其中一个候选作为计划。
正常下一请求来源必须是当前会话已返回且仍保留的候选。建议最多保留两轮完整结果：
已引用来源和最新返回集合；本轮源在计算中固定，发布新集合后淘汰更旧记录。
候选数与消息大小均有界，初始候选数上限建议4；额外增加上限需要容量证据。

缓存模式切片必须与 client 当前承诺前缀精确一致。inline 模式保留相同身份验证，并将
收到的显式前缀同源切片比较；它用于兼容/对照，不作为绕过校验的回退。首版不允许执行端
在承诺后裁剪、平滑或重锚模型动作；若需要转换，须先在两端契约中统一并重新规划。

错 epoch、错摘要、错候选、越界或缓存缺失：模型不执行、不改缓存/RNG，返回现有
InvalidInput 对应的错误。RTC client 将本轮协议/计划失配视为不能正常接续，进入选定
故障处理；不默默拿最新缓存代替、不自动重试旧观测。底层连接是否仍可用与 RTC 是否
还能继续是两件事。模型错误/错误输出继续遵循现有 fatal 生命周期。

reset、断连、服务重启使所有缓存引用失效。产生结果不等于 client 采用结果；
下一次 source 引用才确认其选择。缓存记录不得修改已被引用的内容或复用旧身份。

## 6. 客户端组件与状态转换

建议新增 RTCSession（名称可在实现时调整），独占一个现有 Client 和一个 RPC worker。
控制线程通过非阻塞接口提交快照、查看结果、在动作边界取动作并确认消费；不直接在
控制线程调用阻塞 infer。底层 Client 不开放并发调用，也不增加无界请求队列。

状态建议：

| 状态 | 允许行为/转换 |
| --- | --- |
| UNINITIALIZED | connect、契约检查、配置 reset；不可出动作 |
| BOOTSTRAPPING | 一个空前缀请求在途；由执行端保持启动条件 |
| READY | 有可执行计划；按动作位置消费，到计划周期取快照 |
| IN_FLIGHT | 一个请求在途；只在承诺窗口内继续旧计划；响应放入待校验槽 |
| SIM_WAIT | 不再发环境动作/推进时间；网络线程继续；有效结果→READY |
| FAULT | 不再发正常计划动作；调用执行端安全处理；迟到结果丢弃 |
| CLOSED | 释放连接/worker；不能复用旧 session |

结果接入、动作领取与执行索引变更使用同一短临界区；锁内不做网络等待/模型计算，
大数组校验可先在快照上完成，但提交时仍需重验执行进度与 epoch。

真机 deadline 到达时故障处理必须立即在本地可执行，不等待 RPC worker 结束。
真实安全处理由执行适配器提供，必须说明保持/制动动作、底层队列处理和 watchdog；
不能由 InferPort 统一发送零向量。没有声明这些能力时，只允许假执行器验证，不开放真机模式。

有请求在途的 reset/close：先阻止旧 epoch 出动作并增加本地代次，再中止客户端等待，
让 worker 退出；不并发调用 infer 和 reset。底层模型计算可能继续，server 仍保有所有权；
新连接 busy 应明确呈现，不能声称 close 已取消 GPU 工作或自动重试直到成功。
假模型验证有限清理；永久阻塞模型按现有规则交给进程级处置，不在本版新增强制取消机制。

## 7. PI05Std 与执行适配器接入

### 7.1 模型变长前缀

拟为 PI05Std 增加可选逐样本 prefix_lengths（整数 `[B]`），沿用 action_prefix 存放
`[B,L,A_native]`；没有 lengths 时保持原接口“整批统一 L”的行为。
检查 `0≤length_i≤L` 且不超过训练上限；无效行/非有限输入明确拒绝。

由各行长度生成时间前缀 mask `[B,c,1]`：前缀干净值固定、time=0，后缀正常采样。
无效存储槽不能被当作零动作承诺，也不能影响输出。最终只在真实前缀位置恢复调用者
原始单位动作，避免归一化往返误差。复用已有 euler_integrate 能力，不复制积分器。

动作维度 mask 与时间前缀 mask 相互独立；`mask_padded_action_dims` 两种模式都保持
训练/推理一致，使用保存的 checkpoint 配置，不因 RTC 候选改变动作维度模式。
同一观测的候选复制批次即可建立正确性基线；共享条件缓存优化须在等价验证后再做。
模型输出仅承诺条件和数值契约，不因 CPU 测试通过而宣称闭环更平滑或成功率更高。

### 7.2 服务和执行端

LeRobot 增加明确的 RTC 服务模式/适配器，使用相同 checkpoint/processor校验；
让模型候选 backend 实现第5节内部接口，交由 InferPort RTC 包装层处理缓存和身份。
原有普通 Flow/FAST 服务行为保留；不把 RTC 字段偷偷加给未训练 RTC 的模型。

执行端接入前必须定位实际部署的 InferPort client。读取其项目规范并确认一个模型动作
对应的环境调用与时间：尤其不能把可变时长关节目标误标为固定 Δt，也不能让推理线程
调用不支持并发的仿真 API。用 CPU 假环境走完流程后，再绑定实际仿真和启动策略。

## 10. 验证计划与验收

### 10.1 核心正确性

采用可控假时钟、事件与已知数字动作轨迹，不靠长 sleep 猜测时序：

- 空前缀启动、正常周期；d=p、p+d=c 边界及不合法配置。
- 小于/等于/大于各 d_j 的到达边界；校验前后推进动作的竞争；严格按 k 选择而非 server_ms。
- 前缀和后缀每个绝对动作步最多发一次、不跳步；先到结果不重播，未选候选不二次覆盖。
- 所有候选过期、源覆盖不足、控制周期错过、队列耗尽，均进入明确结果而不是无声继续。
- 错 epoch、错 digest/index/offset、乱序/重复响应、cache miss、模型复用可写 buffer；
  无效请求不调用模型，不改变缓存/RNG；缓存保持有界。
- inline 与 cached 前缀的模型输入及结果一致；单位/通道/配置不一致拒绝。
- realtime 在截止前停止旧计划出队并触发本地处理；simulation_pause 在正确步冻结，
  只增加墙钟等待；RPC timeout 仍能结束等待。
- 在途 reset/close、服务断开与 busy、迟到结果；无遗留 client worker、连接或跨 epoch 动作。

### 10.2 模型与服务

精简模型采用同样的逐候选噪声与输入，比较 batch 与逐条推理，精度容差按 FP32/BF16
分别记录，不要求不同矩阵形状无依据地 bitwise 相同。硬前缀原始单位值必须精确保留。
覆盖候选长度0/1/训练上限、不同batch行、KV cache开关、时间mask与两种维度mask组合、
填充槽扰动不影响结果、旧接口/加载保存行为。校验服务返回与直接模型调用的一致性。
已有积分器已支持逐样本 mask，不通过改写公共积分数学绕过模型入口问题。

### 10.3 性能（执行前需绑定输入与预算）

固定 checkpoint 身份、GPU/驱动、精度、图像/文本长度、c、去噪步数、缓存与编译配置；
比较 batch=1/2/4 的整批端到端延迟、中位数/P95、显存和各阶段耗时。正确同步GPU，
冷启动/编译单列；保留超时/OOM结果。建议起始预算每配置10次预热、100次测量、
总墙钟上限30分钟，一次OOM后停止该配置；这些是待批准预算，不是本轮执行授权。
无变长前缀的初步 batch 测量只能说明计算成本，不能当作真实候选能力验收。

采用多候选的标准：在相同截止窗口下，新增计算后仍能更早接入自由生成后缀，
同时报告错过候选/全局违约比例。硬件数据支持策略选择，不把平均 T_batch/B 当响应延迟，
不把有限样本 P95/最大值当绝对上界，也不由吞吐推出真实机器人成功率。

### 10.4 回归与证据

实施阶段执行 InferPort 新增测试和既有 pytest、ruff check/format、打包与导入检查；
CI 沿用当前 Python/NumPy 兼容范围和跨环境测试，不在本机谎称跑过全部矩阵。
LeRobot 只运行受影响模型/服务检查及必要回归；代码自检与正式审查分别记录，
同一 agent 审查不得写成独立审查。

本会话临时文件、pytest basetemp 和新增缓存放在 LeRobot checkout 的忽略目录 outputs/
下，使用独立运行名并设置 TMPDIR/TMP/TEMP、UV_CACHE_DIR；证据保留到 outputs/validation/。
InferPort 当前不忽略 outputs/，不能默认在其根目录写临时载荷；换机器/工作区时重新
确定可写且被忽略的位置。保持完整模型/数据输入不变，不下载或复制大权重作临时夹具。
仅在确有证据后把摘要和引用写回所属任务，不为每个阶段再造平行状态台账。

## 11. 验收边界

- InferPort 验收：单/多候选契约、正确动作索引、可靠身份关联、两种时钟行为、有限资源与
  错误恢复经过 CPU/localhost 验证，普通业务兼容；不依赖某个模型或仿真 SDK。
- 模型接入验收：PI05Std 逐样本硬前缀及两种动作维度模式成立，原始单位前缀精确，
  模型与服务往返等价。未运行真实设备时不宣称真实 RTC 已验证。
- 性能结论：只针对记录的设备/输入/实现；候选更早接续与闭环质量分别验证。
- 执行端验收：实际入口和时间语义确认，明确设备安全职责；真机支持声明必须有选定设备
  的验证范围。仿真暂停模式不替代真机截止验证。

## 12. 计划确认时需要确定的决策与停止点

建议批准 P1–P3 为第一段实现范围；P4/P5 先补齐各自运行输入与环境，再选择执行。
这只是建议，不能代替用户授权。

需要确认的设计选择：

1. 固定 p、一个在途逻辑请求、完整候选集合一次返回，作为第一版调度/交付方式。
2. 以固定模型动作周期和显式整数步配置为前提；真实可变时长目标如何映射在接入时解决。
3. 采用带 epoch/结果集合身份与摘要的缓存引用，以及有相同校验的 inline 对照路径。
4. 真机超时故障锁定、刷新观测后显式恢复；仿真使用独立的暂停等待模式。
5. 将 PI05Std 变长前缀和服务适配器纳入第一段跨仓库实现，或先只完成 InferPort P1–P2。

遇到下列情况停止对应的依赖工作，继续独立的已授权事项：

- 实际执行器无法保证固定模型动作步、完整暂停或截止后的安全处置。
- 为逐候选抢先返回而需要流式响应/多请求并发，或需要改变现有核心所有权。
- 缓存输入不是实际承诺动作，或相对动作/重采样改变了前缀语义。
- checkpoint 不支持需要的 d_max，或目标GPU/权重/执行入口未绑定；不自动换模型/机器。
- 准备修改超出所选仓库/阶段的实现，或开展未选择的 GPU、仿真、真机实验。

计划通过后将具体选择写入本节，替换相关草案条目。未决事项不能隐式变成默认实现。
