## 本轮取舍依据与交付

- 仿真冻结时间方便调试，但不能验证真实设备的截止要求；当前不增加独立暂停模式。
- 动作 prefix 相比图像很小；显式传输还能准确反映客户端准备后的目标，避免引入服务端
  缓存身份、采纳确认和失效管理。完整 chunk 便于检查 prefix，并保留下一请求所需的后续动作。
- 客户端通过请求关联保存 anchor，使用 `step = anchor + chunk_offset` 对齐动作；目前不需要
  逐动作回传索引。`step` 表示下一待提交命令，设备实际应用进度由执行适配器核对。
- 结果“就绪”包含接收、解码、校验和动作准备。到前缀边界仍未就绪时不继续提交旧动作，
  迟到结果不自动解锁故障；设备停止/保持和控制器队列边界由执行端实现。
  本轮验证没有发现需要修改现有调度规则的问题，运行时代码改动集中于故障上下文和截止余量。
- 共享内存主要优化同机图像传递，本身仍是进程间通信。只有测得收益后才考虑实现，并保持
  请求与帧的绑定、完整写入后发布、读取完成前禁止覆盖、超时/重启后的缓冲区生命周期。
  本机合成载荷结果不能证明目标设备性能或共享内存必然更可靠。
- 多候选先测实际模型 batch=1/2/3/4/5 的整批和端到端延迟，再比较短前缀实际可选比例、
  提前进入新动作的步数和违约率。GPU 耗时接近只是成本证据，不能单独证明候选有收益。
- 当前电脑无需模型、GPU 或仿真即可运行故障测试和图像载荷脚本；真实模型效果、batch 成本、
  相机耗时和设备执行行为留待具备对应平台时验证，不作为本轮已完成项。

## 已确认的用户需求

1. 明确推理启动周期 p、预设最大延迟预算 d、模型完整输出块长度 c。
   p/d 可以按动作步或等效物理时间配置；需要明确两者的换算条件。
2. 采用训练式 RTC 的动作前缀语义：新 chunk 的前缀保持旧计划，更新后续生成部分。
   提前返回仍按动作顺序执行，不重复执行前缀，不跳过尚未执行的前缀。
3. 必须设计超过预设 d 的违约处理与默认安全行为，不能只考虑正常延迟。
4. 请求由 client 发起，执行进度由 client 指定。仿真进度不能由 server 的墙钟推算。
   方案必须覆盖仿真与真实物理场景。
5. 支持讨论两种前缀来源：client 直接发送数组；client 引用 server 缓存的动作块。
   缓存引用必须核对身份和切片位置，不允许误用另一动作块。
6. 请求除观测外需要携带必要的动态对齐信息。固定配置可在建立会话时约定，
   配置改变须有明确同步机制，不能造成双方解释不一致。
7. 用户已确认暂缓共享内存，本次集中讨论 RTC 时序；不引入新的传输实现。
8. 真机不得在预设最大承诺窗口之后继续消费旧 chunk；需要受监管的等待/安全处理。
   等待的设备动作和恢复规则待定。用户提出仿真可暂停等待，这一模式的语义需明确。
9. 多 GPU、batch 内不同前缀长度同时预测，并按实际耗时选择候选，纳入方案分析；
   尚未选定实现或授权性能实验。

## 时序讨论与术语澄清（未批准为最终方案）

### p、d 与实际延迟

建议 p 表示相邻推理请求的启动间隔；d 是提前选定的覆盖预算，不是每次实际耗时 L_i。
c 是包含前缀的完整输出长度。动作步必须对应模型动作采样步，不能直接混同底层伺服 tick。
若动作周期固定为 Δt，时间预算 D 对应 d=ceil(D/Δt)；非固定时长目标需另行定义。
端到端 L_i 应从观测/执行锚点量到结果在执行端可用，不能只统计 GPU 时间。

单工作者串行条件下，下一请求实际启动不得早于上一请求完成。
固定周期且希望覆盖所有 L_i≤d 的情况，选 p≥d；严格物理约束来自实际 L_i，
不是把人为设定的 d 误当作每次必然消耗的时间。
在每轮正常完成、前后 chunk 起点相差 p、单个旧 chunk 提供前缀的模型下，
还需 p+d≤c，保证旧 chunk 能覆盖下一轮推理窗口。
这组约束的单位、启动流程、控制边界余量及允许的等号需在最终方案中明确。

可比较的方案（仅用于分析，不代表选用）：

- 固定 p/d、串行单个在途请求：作为比较基线；最终方案尚未选定。
- 串行动态周期：忙时跳过/推迟触发，不排队累积陈旧观测；实际 p_i 改变，须重新检查覆盖。
- 动态前缀预算：下一请求前估计 d_i，并受模型训练上限与剩余动作约束；
  已发出的请求不能事后改变条件前缀。固定预算和动态估计都不能保证绝无超时。
- 多个并行模型请求：其他系统可设计，但有资源竞争、旧观测、前缀依赖与结果顺序问题；
  当前 InferPort 无此请求调度能力。用户已要求讨论多 GPU/多前缀候选，未选定具体实现。

首块启动/预热、首份观测到动作启动的时间关系也需单独定义，不能假设启动时已有前缀。
对于训练式 RTC，前缀长度须受 checkpoint 的训练支持范围约束。

### client 时钟与仿真

建议区分 client 的动作序号/环境逻辑时间和本地单调墙钟：前者确定动作对齐，
后者测量通信与计算耗时。server 不按收到请求后的墙钟自行推进执行索引。
观测、当前计划身份、下一个待执行动作位置必须形成一致快照。

待选择：实时节拍仿真、尽快推进的异步仿真、按指定逻辑延迟注入的仿真如何表达。
三者的墙钟和环境时间映射不同，不能混报为同一实时延迟实验。
仿真在等待推理期间暂停推进不能自动算作成功的并发 RTC 验证。

### 提前完成与超时

提前结果按当前执行位置合并，未执行的承诺前缀继续保留，不能从新块第 0 步重播。
超过 d 后，实际执行可能越过硬前缀范围；直接丢掉新块前若干步并不保证条件一致。

默认违约策略待定。建议候选为：不接纳失配的新计划，进入显式故障/恢复状态，
通知执行适配器调用预先声明的安全处理。必须区分停止发新命令和实际停止机器人，
包括已下发控制器队列的处置；零动作、保持末值或断开连接均不自动等于安全。
真实设备的保持/减速/停止由控制模式与设备适配器定义；无明确处理能力时拒绝启用对应模式。
用户进一步明确：真机超出预设最大窗口后不继续消费旧 chunk。候选策略是在执行端
进入受控等待/安全处置；具体控制指令、已下发队列、等待期限和恢复条件仍待确定。
仿真暂停等待模式下不必把墙钟等待判成 episode 失败；实时仿真需要另行记录超时。

## 服务端前缀缓存讨论（未定协议）

- 执行端是计划采用情况与执行进度的权威；server 最近生成的块不一定已被采用。
- 候选关联信息包括 session/episode epoch、chunk_id、观测对应动作步、切片起点/长度；
  确切字段及哪些配置会话级固定，待设计。请求序号与已采用 chunk 身份不能混为一谈。
- server 应据明确引用定位缓存，校验会话、动作语义/配置、覆盖范围与合法切片。
  若需要内容摘要，应明确规范化字节表示；摘要不能替代执行位置/语义校验。
- client 需承诺被引用前缀确实是期间将执行的动作。裁剪、平滑、重采样、相对动作重锚等
  处理可能使缓存不再等于执行命令，需限制处理位置或同步实际前缀。
- 缓存缺失、引用过期、错块、重置、重连和结果未被采用均需明确响应；不能静默取最新块。
  缓存保留/释放与确认机制，以及显式前缀的回退条件，待定。
- 开销量级：14 维 × 10 步 × FP32 的前缀仅 560 字节；图像通常是更大的传输载荷。
  不以未经测量的提速作为引入服务端状态的唯一理由。

## 多 GPU 与多前缀候选：进一步讨论（2026-11-12）

用户提出：同一观测下并行生成不同 d 的动作块，结果回来后按真实耗时选择适合的块，
减少固定长前缀造成的反应延后。以下是可行性推导，尚无实现/性能或闭环效果验证。

### 预算与候选长度分开

建议将全局最长等待/旧计划承诺窗口记为 d_max，各候选前缀记为 d_j。
一次候选的硬前缀必须在生成前确定；生成结束后裁短长前缀不会等价于短前缀条件生成。
所有候选使用同一观测锚点和旧计划快照，在各自前缀范围内与该旧计划一致。

当候选在 client 可接入时，令 k 是从观测锚点到最早可接入动作边界的已推进动作步数。
选择条件至少包括：已完成且收到、k≤d_j≤d_max、计划/会话未失效、期间执行命令与
该候选假设一致、仍有可执行后缀。边界交接须原子化并留出传输/调度余量。
在这些条件满足的候选中，最短 d_j 给出最早的自由生成动作位置；不是选离 k 最近的值。
若 d_j>k，剩余前缀仍须执行；若 d_j<k，不能只靠裁掉前面动作认为仍然正确。
在 client 最终接入前需重验 k，server 的推理完成时间不足以作最终选择。

例：Δt=20ms，候选 d_j={5,6,8} 步（100/120/160ms）。所有结果在 client 于105ms
可用、可在120ms边界接入时，k=6，选择6步候选；固定8步前缀则要到160ms才进入
自由生成部分。该例只展示时间语义，不是模型速度或真实设备测量。

一旦采用某个候选并改变后续计划，其余基于旧计划的候选不能再自动覆盖队列；
应丢弃或重新验证与已承诺动作的兼容性。已采用计划身份和执行进度仍由 client 决定。
小 d_j 的候选错过期限不等于全局超时；可以在 d_max 之内等待仍可用的较长候选。
全部候选不可用或到达 d_max 仍未收到可接入结果，进入违约处置。
候选长度受训练上限和旧计划覆盖限制；多候选情况下 p+d_max≤c 的旧块覆盖条件
仍需按实际启动间隔/锚点检查，并行并不消除这一约束。

### 计算并行与现有接口缺口

- 同一条 Flow Euler 轨迹的下一步依赖上一步的状态，不能简单把相邻去噪步分到不同 GPU
  同时求值。单次前向可研究张量并行，但通信成本可能抵消收益，不能保证延迟降低。
- 每卡一份模型，分别计算不同 d_j：候选相互独立，可并行；不必然缩短每条候选本身的耗时。
  同机 batch 可利用并行计算，但增加 batch 可能推高整体延迟，必须测量端到端收益。
- 同一 batch 的结果通常一起返回；多个 GPU 若要逐候选返回，需设计响应交付方式。
  当前 InferPort 一个 infer 返回一个完整结果；内部多 GPU 计算并一次返回候选集合与
  多请求流水/结果流是不同改动，不应自动扩大到多客户端或流式协议。
- 不同观测错峰推理也可研究，但更新频率不等于单次延迟，且旧请求的承诺前缀可能因
  前一结果采用而失效；必须校验，当前不作为已选方案。
- 本次源码核对：PI05Std sample_flow 由 action_prefix.shape[1] 为所有 batch 行设置
  同一个硬前缀长度；尚无逐样本 prefix_lengths 接口。零填充短前缀会把后续零动作
  也当成已知前缀，不等价于变长条件。需要逐样本硬前缀 mask/时间条件与验证。
  现有部署适配器接受单请求 [prefix_steps,14] 并加 batch 维，也未暴露候选集合。
- 同一观测的视觉/语言条件有复用机会，但当前缓存复用范围、跨设备传输成本需核对和测量，
  不能把它视为已经实现的优化。

### Batch 延迟假设与待测量项

2026-11-12 补充：用户询问 RTX 5090 上 batch=1 与 batch=4 是否接近等时。
当前没有这组针对实际 PI05Std 工作负载的实测，不能给出延迟倍数，也不根据 GPU 型号
推断候选方案一定有效。对话中的示意毫秒数不是测量结果，不作为预算依据。

GPU 同时利用样本内部与 batch 之间的并行；batch=1 不代表仅使用少量 GPU 资源。
若工作负载受算子启动、权重读取或小矩阵效率限制，增大 batch 可能仅少量增加耗时；
若计算、激活带宽或缓存已形成瓶颈，整批耗时可能明显增加。吞吐改善不等于单次响应更快。
RTC 关注整批结果在 client 可用的时间 T_batch，不能用 T_batch/batch_size 作为响应延迟。

待比较的计算路径：

- 复制观测执行完整 batch：视觉/语言条件与动作采样都按 batch 计算。
- 研究只计算一次相同观测的条件缓存，再对不同前缀并行采样；这是候选优化，尚未实现。
- 多 GPU 各计算候选：区分等齐返回与逐候选交付，不预先承诺任一路径更快。

后续可提议的最小测量（尚未获执行授权、未执行）：在同一 checkpoint、GPU、精度、
图像/文本形状、chunk size、去噪步数及缓存/编译设置下比较 batch=1/2/4；预热后测
整批延迟分布（至少中位数与 P95）、显存，并区分预处理、条件编码、去噪与端到端耗时。
须正确同步 GPU 计时；冷启动/编译与稳态分开；记录并发负载和样本数。有限样本的最大值
或 P95 不能作为绝不超时的保证。当前未支持异长前缀的 batch 测量，只能提供计算成本
基线，不能代替未来真正多前缀候选实现的正确性与性能验证。

采用候选方案的依据应是：计入 batch 额外耗时后，按 client 接入边界仍有更短前缀候选
可用，实际更早进入自由生成动作，同时违约率满足选定标准。不能仅凭吞吐提高作决定。
候选数量/长度、共享缓存、GPU 分配、交付方式及性能门槛仍待方案选择。

### 真机等待与仿真暂停

真机到 d_max 后停止消费旧计划，是用户明确提出的约束；环境的物理时间不会暂停。
受控保持/制动需要执行端实现，进程阻塞等待不代表实际安全。进入等待后，状态可能
偏离原推理假设；迟到结果不能自动恢复动作，建议刷新观测并显式恢复，最终规则待定。
监管应在 client 本地，不依赖 server 及时返回；底层控制队列也不能越过承诺边界继续出队。

若仿真允许在承诺窗口末冻结完整模拟状态及其事件时间，等待只增加墙钟耗时，
不推进环境动作步；这种模式可以避免动作时间线上的超时，但不验证真机截止时间能力。
暂停期间若仍有外部事件/传感输入/时钟推进，则不满足完整冻结假设。
实时节拍仿真不能通过暂停隐去违约；应保留实际延迟、暂停时长与时钟模式。
另外，冻结模拟时间不取消 InferPort 的网络请求超时；等待模式仍需有限的传输/服务
故障处理，以免服务失效后永久挂起。初始请求即暂停与执行完承诺前缀后再暂停需区分。

## 共享内存与本次范围

2026-11-12 用户已确认：共享内存先放一放，本次集中讨论时序。保持现有 WebSocket
作为通信现状，不实施共享内存；未来是否另立实现任务由后续需求决定。

同机不同进程可共享大数组，小消息通道负责通知和元数据；跨机继续消息传输。
共享内存仍需快照一致性、读写所有权、覆盖保护、同步及资源生命周期，
也不自动消除预处理或 CPU→GPU 拷贝。当前不引入通用传输插件框架或未选定的新后端。

## 设计阶段完成标准与后续验证清单

设计阶段完成须形成并确认：

1. p/d/c 单位、观测与动作的锚点、首块启动、正常/提前/超时的具体时间线与约束。
2. 仿真与真实执行时钟契约；固定与动态策略的选择及例外处理。
3. 显式前缀/缓存引用的身份、校验、确认、生命周期与错误处理规则。
4. 默认违约处置及执行适配器责任，解释队列耗尽、重置和迟到结果处理。
5. InferPort、模型适配器和执行端的职责与最小接口变更；保持共享内存已暂缓的范围。
6. 获批的实现范围和分层验证计划，保留尚未验证的真实性能与设备行为。

建议验证场景（尚未执行）：确定性假时钟与可变延迟；提前/边界/超时；前缀不重播；
错块/旧会话/越界引用/缓存缺失；重置时有请求在途；执行端修改动作；时钟速度不同；
结果迟到及队列耗尽；显式前缀与缓存引用等价；通信与模型耗时分开统计；
batch=1/2/4 的整批延迟与候选实际接续时间比较（见上面的待测量项）。
设备实验需另行绑定环境、策略、资源和授权，不因建立任务而启动。
