# InferPort 成熟度评估与后续计划

评估日期：2026-09-26。代码基线：`fb7f0b0`，InferPort 0.1.0。

本文记录后续工作的优先级、完成标准和暂缓事项，供恢复开发时查阅。
当前 API、协议与职责边界由 [设计文档](inferport-design.md) 定义；
已运行的检查、结果和适用范围统一保存在 [验证记录](validation.md)。
这里的后续计划不表示相关能力已经实现或完成发布。

## 当前判断

InferPort 已具备可用的首版核心：独立安装、WebSocket / MessagePack 通信、NumPy 数组交换、
错误与超时处理、状态清理、示例、测试及打包均已实现，首次 GitHub CI 已通过。
接下来的重点是实际接入证据、版本发布和兼容性维护。

目前已有的多 Python / NumPy 环境验证使用同一版 InferPort，不能替代不同 SDK 版本之间的互通验证。
无状态与有状态示例、短期资源检查也不能替代真实模型和长时间运行验证。

## 优先事项与完成标准

下表各项均为后续工作；已经取得的测试证据不在这里重复维护。

| 优先级 | 工作 | 当前缺口 | 完成标准 |
|---|---|---|---|
| 最高 | 真实模型与执行端接入 | 尚无真实模型、processor 和执行环境的集成结果 | 至少一组模型仓库与执行仓库独立安装 InferPort，完成输入输出、状态重置、错误处理及本地/远程推理一致性验证，并记录复现步骤 |
| 高 | 版本与发布流程 | 版本来源、元数据和发布工作流已整理；尚待远程发布流程与 PyPI 上传验证 | 变更记录、tag、发行元数据和构建产物对应；发布步骤及干净环境安装验证可复现 |
| 高 | 协议兼容性保障 | 尚未固定独立于当前实现的协议样本；缺少 SDK 升级后的互通策略 | 保存有效及非法协议样本，明确 API/线协议的变更规则；后续版本与已发布基线进行客户端/服务端双向互通测试 |
| 中 | 持续运行验证 | 已有短期故障与资源检查，尚无长时间运行证据 | 按实际载荷持续推理并反复连接、重启服务、模拟网络中断；记录持续时间、调用数、资源趋势、延迟与恢复结果 |
| 中 | 接入文档与故障排查 | 当前示例主要使用 NumPy 后端，缺少完整真实接入教程 | 新使用者能按文档完成模型端与执行端适配，并定位连接失败、busy、首次加载超时、消息超限及 TLS 配置问题 |
| 中 | 开发维护规范 | 已有部分类型标注与 py.typed，尚无类型检查；缺少简短贡献指南 | 公共 API 纳入一种类型检查工具；说明开发命令、测试边界、版本支持与弃用方式，使贡献者能独立完成修改和验证 |

### 真实接入需要回答的问题

- 模型仓库是否只需少量适配代码，且无需将其内部类暴露给通信库？
- 执行仓库能否独立安装、调用及处理错误，不依赖模型仓库的 Python 环境？
- 在相同输入、模型状态与可控随机性下，本地推理和远程推理是否在预先约定的数值容差内一致？
- 图像布局、batch、动作序列、processor 状态和 reset 语义是否能清楚约定？
- 超时、断连及重新创建客户端时，执行端和模型端是否按约定处理状态？

首个后端可从已有 LeRobot / PI05 适配或 mimix 中选择，具体模型、权重与执行环境尚未选定。
适配器和模型/机器人依赖留在各自业务仓库，InferPort 保留通用接口、轻量示例及验证方法。
离线推理一致性、仿真闭环和真机闭环分别记录，不能相互代替。

### 发布整理的具体范围

版本号已统一由 `src/inferport/__init__.py` 提供，元数据包含仓库与问题反馈链接，
已补充 [变更记录](../CHANGELOG.md)、[发布步骤](releasing.md) 与产物安装检查。
项目署名已统一为 InferPort contributors，MIT 条款保持不变。

公开发布前确认 PyPI 名称可用性；可使用 [TestPyPI](https://packaging.python.org/en/latest/guides/using-testpypi/)
演练上传与安装，并采用 [Trusted Publishing](https://docs.pypi.org/trusted-publishers/) 进行发布认证。
发布准备与实际上传分别记录，不把本地构建成功视为已经发布。

### 协议与稳定性验证的边界

固定协议样本应来自已确认的 v1 契约；测试不能只用同一实现即时编码后再解码。
同时覆盖错误响应与不支持的协议版本。明确哪些改动能保持兼容、哪些必须升级线协议，
并给公共 Python API 的破坏性变更与弃用留出可理解的升级路径。

持续运行测试根据实际输入大小和部署环境确定时长与资源预算，避免凭空承诺性能指标。
网络恢复仍由应用重新创建客户端；不为测试恢复路径引入自动请求重放。
若需要优化，先区分网络、序列化和模型执行的开销，再决定是否修改实现。

## 建议实施顺序

1. 完成一轮简洁的发布整理：版本、元数据、变更记录、说明文档和发布验证步骤。
2. 集中完成第一组真实模型与执行端接入，以实际结果检查“三个仓库”的职责分工。
3. 根据接入反馈完善协议兼容测试、持续运行测试和故障排查文档；公共 API 类型检查可穿插进行。

真实接入最有价值；先做发布整理，是因为这部分范围明确且不依赖模型权重或设备。
正式承诺稳定接口前完成对应兼容规则，正式部署到具体设备前完成相应集成验证。

## 暂缓事项

现阶段继续保持一模型、一活动连接、数组自身承载 batch 的范围。
RTC、动作调度、自动批处理、多客户端/多模型、更多传输后端、通用 schema 和服务描述框架，
均等待实际接入提出明确需求后再评估，不以增加这些功能作为成熟度目标。
当前 Python >=3.10、NumPy >=1.21.3,<3 的兼容方向保持不变。

## 后续维护方式

恢复工作时先核对代码、最新 CI 与验证记录，再从本文件选择具体工作范围。
完成一项后更新此处对应缺口，并将实际命令、环境与结果补入验证记录；
API 或协议约定发生变化时同步设计文档。保留失败、未运行和平台限制，避免将建议写成已实现承诺。
