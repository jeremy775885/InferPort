# InferPort 后续计划

更新日期：2026-11-16。已发布基线：`v0.2.0`；当前源码为 `0.3.0` 未发布候选。
基础 RTC 已在 `716f252` 实现；本轮补充无需模型的故障验证、诊断和载荷测量工具。
已完成事项和限制见 [验证概览](validation.md)，本文件只维护剩余工作的优先级。

## 0.2.0：公开数据契约

0.2.0 已实现必需的 describe、类型化数据契约与 joint-targets.v1 profile，来自实际接入需求。
所有后端直接使用新接口；不保留旧 Backend 的无规格运行分支或兼容层。
Client 建连时缓存契约并校验收到的结果；接入方声明诊断和模型 seed 等扩展，业务代码保留状态检查。
该阶段发布为 0.2.0，通信统一为不带版本后缀的 inferport；两端按当前接口更新。
不再引入单独的协议版本代号；历史发布 CI 不能代替当前候选的验证。

## 下一阶段：真实模型与执行端接入

按 [真实推理验证计划](integration-validation.md) 选择一个模型和执行端，依次完成：

1. 固定观测下的原生模型、本地适配器、远程推理对照。
2. 跨机器通信、状态重置、异常恢复与持续运行验证。
3. 选定仿真或真机环境的闭环验证。

当前接入方为 LeRobot PI05 与 RoboTwin；先前未发布候选已有 CPU/跨环境验证和 GPU 闭环 10/10。
本次通信标识调整的检查范围单独记录，不将先前结果改记为新候选实测。适配器留在各自业务仓库，
以两端独立安装、适配代码量、数值一致性和实际运行结果检查接口是否满足需要。
阶段步骤和验收标准统一维护在接入计划中。

## 后续维护优先级

| 优先级 | 工作 | 完成标准 |
|---|---|---|
| 高 | 协议一致性 | 保存独立编码器的消息样本；验证同一候选双向互通与通信标识不匹配时明确失败 |
| 中 | 持续运行证据 | 按真实载荷记录运行时间、调用数、资源趋势、延迟及断网/服务重启后的恢复结果；具体场景沿用接入计划 |
| 中 | 接入文档与故障排查 | 将首次接入整理成可复现教程，覆盖连接失败、busy、首次加载超时、消息超限及实际部署遇到的问题 |
| 中 | 开发维护规范 | 公共 API 纳入一种类型检查工具；补充简短贡献指南，说明开发命令、测试边界、版本支持与弃用方式 |

现有跨环境测试仅证明同一 SDK 在不同 Python/NumPy 环境间互通；短期资源检查不能代替长时间运行。
性能优化先区分通信、序列化和模型执行成本，实际问题与需求决定后续改动。

## RTC：当前方案与后续验证

- 当前采用单候选、客户端显式 prefix、服务端返回完整 chunk；动作起点和进度由客户端维护。
  截止与前缀边界限制旧动作提交，故障后不自动接纳迟到结果。使用与诊断见 [RTC 文档](rtc.md)。
- 无模型测试和合成图像载荷基准可在普通电脑运行；结果和限制记入 [验证概览](validation.md)。
- 下一步在实际接入中核对观测采集/复制的控制线程耗时、控制器队列和故障处置，
  记录端到端延迟、截止余量和违约率。CPU 测试不代表设备执行或模型效果验证。
- 图像共享内存先测目标机器上的编码、复制和 localhost 传递成本，再决定是否做原型；
  多候选先在模型仓库测 batch=1/2/3/4/5 的整批延迟及短前缀收益，再决定接口扩展。
- [RTC-001](tasks/RTC-001.md) 与[原实施草案](tasks/RTC-001-plan.md)已就地归档，
  保留设计依据和收尾说明，不再作为待逐项实现的清单。

## 暂缓事项

保持一模型、一活动连接、数组自身承载 batch 的范围。
仿真暂停移出近期开发范围；服务端动作缓存、chunk 裁剪和逐动作网络索引不列为当前待办。
自动批处理、多客户端/多模型、更多传输后端，
等待实际接入提出明确需求后再评估。
Python >=3.10、NumPy >=1.21.3,<3 的兼容方向保持不变，具体约定见 [协议与接口参考](inferport-design.md)。

## 维护方式

恢复工作时先核对当前代码、CI 和验证概览，再选择具体工作范围。
完成一项后更新此处对应缺口，把环境、命令与结果补入验证记录；保留失败及未运行项目。
API 或协议发生变化时更新接口参考，发布新版本时更新 [CHANGELOG](../CHANGELOG.md)，
并执行 [发布指南](releasing.md)。历史实验细节保存在 `docs/archive/`，后续结果另行记录。
