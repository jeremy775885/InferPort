# 真实推理接入与验证计划

更新日期：2026-09-26。起始基线：InferPort `0.1.0`，线协议 `inferport.v1`。

当前协议库首版实现、自动化测试及 PyPI 发布已完成，可暂时结束集中开发。
下一阶段用一组真实模型和执行环境检验接口与通信链路；本文件是待执行计划，尚无真实接入结果。
已有证据见 [验证记录](validation.md)，其他维护事项见 [roadmap](roadmap.md)。

## 目标与三个仓库的分工

目标是让算法库与执行环境各自安装 InferPort、编写少量适配代码，即可交换真实推理输入和结果。
两端使用独立 Python 环境，首次验证固定安装 `inferport==0.1.0`，记录各自依赖版本。

| 仓库 | 负责的内容 | 本次交付物 |
|---|---|---|
| 模型算法库，如 LeRobot 或 mimix | 模型与权重加载、processor、设备与张量转换、推理和状态清理 | `Backend` 实现、调用 `serve()` 的启动入口、原生推理对照脚本 |
| InferPort | 通用 Payload、序列化、通信、连接与错误语义 | 接入方法和结果索引；实际接入发现通用缺陷时补修复及相应测试 |
| 执行环境库，如机器人、仿真或离线回放程序 | 采集观测、组装输入、调用 `Client`、解释和执行结果、控制循环 | 客户端入口、输入输出约定、验证脚本和运行记录 |

模型及机器人依赖、业务适配器保存在各自仓库。InferPort 保持通用接口；
RTC、动作调度、多模型、多连接、其他传输后端和通用 schema 框架仍按 roadmap 暂缓。
离线回放可以作为首个客户端，后续再接入仿真或真机。

## 开始前选定的最少信息

以下信息尚未确定，下次开展接入时填写，无需为了补文档提前选定设备或模型：

| 项目 | 需要记录的内容 |
|---|---|
| 模型 | 选择一个当前可运行的模型；算法仓库、提交、原生推理入口。已有 LeRobot 适配或 mimix 均可作为候选 |
| 权重与配置 | checkpoint 的位置和版本/校验信息，模型配置、processor 与归一化参数 |
| 输入数据 | 可复现的图像、状态、任务指令及来源；先准备同一段固定观测序列 |
| 客户端 | 所属仓库、提交；第一轮使用回放、仿真还是真机，以及后续闭环环境 |
| 运行环境 | 两端 Python/依赖、CPU/GPU、设备与精度、网络和服务地址 |

最先完成一次原生模型推理，并保存输入、输出和启动命令，作为后续比较基线。
若尚无机器人或仿真环境，可独立完成下面的第 1、2 阶段，闭环结果继续标记未验证。

## 先约定业务数据

在适配器所属仓库写明以下内容，InferPort 不统一命名这些业务字段：

- 输入字段、必选/可选项，图像 RGB/BGR、HWC/CHW、分辨率、dtype、取值范围与相机顺序。
- state 的关节顺序、坐标系、单位，batch 维度和样本顺序，任务指令放在输入还是 reset 上下文。
- 预处理、归一化和动作后处理由哪一端完成，保证每项转换只执行一次。
- 输出字段、shape、dtype、单位；返回单步动作、动作 chunk、value 或 reward 的含义。
- 若返回动作 chunk，由执行端决定消费多少步、何时重新观测和推理；传回完整 chunk 不等于 RTC。
- 模型、processor、缓存和随机状态的归属；`reset({})` 能清理会话，带上下文的 reset 完整替换上下文。

Torch/JAX 等张量由模型适配器显式转换为受支持的 NumPy 数组；设备迁移和 dtype 转换也由适配器负责。
接口与生命周期细节以 [设计文档](inferport-design.md) 为准。

## 分阶段执行与验收

### 1. 真实模型与固定观测的推理对照

1. 在两端各自的虚拟环境中安装已发布版本：
   `python -m pip install --index-url https://pypi.org/simple inferport==0.1.0`。
2. 实现模型端 `Backend.infer()`，按需要实现 `reset()` 和 `close()`；先验证适配器本地调用。
3. 启动独立服务端与客户端进程，先在同机回环地址传输真实图像、状态和指令。
4. 对比三条路径：原生模型入口 → 本地适配器 → 经 InferPort 调用的适配器。
   各路径使用相同权重、配置、输入和初始状态；有状态模型回放完整观测序列，每次比较前重置。
5. 检查字段、shape、dtype、数值、非有限值及动作含义，记录差异和实际判定结果。

完成标准：可从命令和固定数据复现三条路径；输出满足事先约定的容差与业务含义。
数值容差由模型精度确定，不能为了让结果通过而临时放宽。
随机模型应控制各路径的 RNG 状态；仅设相同 seed 仍不确定时，记录原因并事先定义统计比较方法，
不以单次近似输出声称严格一致。

### 2. 跨机器通信、会话与异常恢复

将同一套输入放到实际部署网络重复调用，两端保持独立依赖环境。
服务端显式设置可访问的监听地址，客户端使用对应 URI；记录双方消息上限、超时和实际部署配置。

| 场景 | 需要验证的行为 |
|---|---|
| 连续调用和 episode 切换 | 输入输出顺序正确；显式 reset 后模型和 processor 均无上一轮残留状态 |
| 首次加载 | 模型成功加载并进入 READY；`open_timeout` 能覆盖实际加载时间。线程绑定资源按设计在工作线程创建和使用 |
| 输入错误 | 适配器先校验再改变状态；`InvalidInput` 返回后，同一连接能继续处理合法请求 |
| 推理超时或连接中断 | 执行端处理错误，不消费本次已失效的结果；后端完成在途工作并清理后，可创建新 Client 恢复 |
| 服务重启 | 应用创建新 Client，并按业务需要显式恢复任务上下文；旧会话状态不会自动恢复 |
| 重复运行与关闭 | 模型不会在每次 reset 时重新加载；记录资源变化、关闭结果和出现的异常 |

超时不会取消已开始的模型计算，新连接在旧工作和清理完成前可能收到 `busy`。
InferPort 不自动重连或重放请求；应用负责决定何时重新接入、重新观测和继续执行。

记录预热次数、样本数、请求/响应大小、客户端完整 `infer()` 调用的 p50/p95/p99 和超时数；
将冷启动与预热后的结果分开。按需要测量适配器预处理、模型计算、后处理以及序列化成本，
GPU 计时须说明同步方式；不能把总往返耗时全部当成网络耗时。
持续运行时记录时长、调用数、两端内存/显存、线程和文件描述符趋势，阈值由目标环境确定。

完成标准：跨机器推理满足既定数值和时延条件，上述恢复路径可复现，持续运行结果有记录。
本轮测试的时长和网络条件必须写明，不能据此泛化到所有部署。

### 3. 仿真或真机闭环

在执行环境自身的控制循环中完成采集观测、推理、消费动作及 episode 重置。
验证动作顺序、单位、chunk 消费方式、实际控制频率和超时后的执行行为。
记录任务、episode 数、运行时长、任务表现、延迟和失败原因，并与原有执行方式对照（若有）。

完成标准：选定环境能连续完成约定任务，状态重置和故障处理符合执行环境的约定。
仿真与真机分别记录；离线数值一致不代表闭环成功，仿真通过也不代表真机已验证。

## 结果记录与后续决策

详细运行日志、输入样本和模型相关脚本留在对应业务仓库；InferPort 的
[验证记录](validation.md) 增加结果摘要、复现入口和明确的未验证项。
每次记录至少包含：

- 日期、验证阶段、两端仓库及提交、InferPort 版本、依赖和硬件/网络环境。
- 模型/权重/processor、数据集或样本标识、完整启动与调用命令、实际参数。
- 预期标准与实测结果：数值差异、时延、调用数、资源趋势、错误与恢复情况。
- 适配器路径和代码规模，需要触碰的模型/环境内部接口，以及是否修改了 InferPort。
- 通过、失败、未执行的项目；剩余问题属于算法、业务适配、通信库还是部署环境。

优先用这一轮结果回答：两端能否独立安装，适配代码是否足够少，原生与远程推理是否一致，
实际时延与恢复行为是否满足目标环境。
发现通用问题时再修改 InferPort 并补相应回归测试、文档和版本；
若接口已满足需要，继续在业务仓库推进模型与执行环境的适配。
